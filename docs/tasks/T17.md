## 필수 계약/참조
contracts.md projects/repository/runs, T01/T03/T10. 프로젝트 삭제는 아래 범위에 한해 append-only 규칙의 명시적 예외다. 개별 snapshot 변경 권한으로 확대하지 않는다.

## 구현 순서
1. PATCH /api/projects/:id 입력 {expectedRevision,title,budgetMicros}, 반환 Project. 제목/예산은 CreateProject와 동일 검증, CAS revision+1. ID/createdAt과 과거 run snapshot 불변.
2. 예산 하향은 허용하되 이전 비용을 지우지 않는다. 새 submit은 변경된 예산으로 기존 누적 비용 규칙을 적용한다. 이미 접수된 run은 취소하지 않는다. UI에 예산을 낮춰도 기존 과금이 취소되지 않음을 설명한다.
3. DELETE /api/projects/:id 입력 {expectedRevision}, 성공 {data:{id,deleted:true}}. 같은 프로젝트 active run(unknown/download_failed 포함)이 있으면 CONFLICT. missing은 NOT_FOUND, stale revision은 CONFLICT.
4. repository에 프로젝트 단위 삭제 연산을 명시하고 동일 동기 transaction에서 존재/CAS/active 검사 및 해당 프로젝트 모든 aggregate 삭제. FK와 JSON 참조 순서를 명세하고 rollback 검증. submit과 delete 경쟁은 transaction으로 직렬화한다.
5. content-addressed blob은 다른 프로젝트와 공유될 수 있으므로 물리 삭제하지 않는다. 프로젝트 DB 기록만 삭제, 디스크 공간 즉시 회수/완전한 비밀 삭제를 약속하지 않는다. API로 삭제된 media/export 접근은 NOT_FOUND.
6. 목록에 편집/삭제 버튼과 제목을 명시한 삭제 확인 UI. 취소 시 요청 0회. 삭제 성공 후 선택 projectId 및 종속 scene/candidate/run query를 정리하고 목록 재조회. 다른 열린 화면도 404를 안내하며 성공 상태를 가장하지 않는다.

## 인수 기준
제목·예산 수정/재조회·새로고침 반영; 빈 제목·음수 예산 거부; stale CAS 실패; 기존 snapshot 불변. 삭제 취소 0회, 성공 후 모든 프로젝트 record 조회 불가; 다른 프로젝트/공유 blob 정상; active 상태별 삭제 차단; 실패 시 부분 삭제 없음; submit/delete 동시 요청으로 orphan run 생성 없음.

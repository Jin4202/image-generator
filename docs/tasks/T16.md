## 구현 순서
1. /settings에 password 입력 ‘fal API 키’, 저장/교체/삭제, provider 모드 선택(mock/fal)을 제공한다. 저장 후 입력을 비운다. 기존 키를 브라우저로 다시 보내지 않는다.
2. GET /api/settings/fal은 configured/source(env|file|none)/저장된 모드/현재 서버 모드/restartRequired만 반환. PUT은 mode와 선택적 key(생략=유지, 비어 있는 값=VALIDATION), DELETE는 파일 키 삭제와 파일 모드 mock 전환. 성공 envelope는 기존 규칙을 따른다. 정확한 Zod DTO와 응답 타입을 계약 단계에 고정한다.
3. APP_DATA_DIR 내부 별도 settings.json에 서버가 atomic replace로 저장(파일 0600, 상위 전용 디렉터리 0700). 평문 로컬 저장임을 UI/README에 명시. DB/workspace/manifest/localStorage/cookie에 키를 저장하지 않는다. 기존 same-origin/loopback 검사를 사용하고 오류/로그에 키를 넣지 않는다.
4. 우선순위는 명시적 환경변수 > 설정 파일 > 기본 mock. FAL_KEY 환경변수는 파일 키보다 우선한다. 환경변수 우선 적용 상태를 UI에 표시하고 환경변수를 UI에서 수정/삭제한다고 표시하지 않는다.
5. 첫 버전은 서버와 worker를 모두 재시작해야 적용. 키 저장만으로 유료 모드를 즉시 켜지 않는다. 서버·worker는 동일 파일/환경 규칙을 시작 시 읽는다. 저장 직후 재시작 안내; 새 설정 적용 전 available을 거짓으로 올리지 않는다. worker hot reload는 구현하지 않는다.
6. active run(unknown/download_failed 포함)이 있으면 키/모드 변경과 삭제를 CONFLICT로 거부한다. 설정 변경과 신규 submit의 경쟁 방지 방식을 계약 단계에서 확정한다(단순 UI 검사 불충분). 설정 저장은 fal API를 호출하지 않으며 ‘저장됨’과 ‘유효한 키로 인증 확인됨’을 구분한다.

## 인수 기준
키 입력→저장→서버·worker 재시작 후 동일 설정 적용; 환경변수 우선 적용; 키 삭제→재시작 후 mock; 잘못된 입력/권한·쓰기 실패 시 기존 파일 유지; active run 변경 차단. sentinel 키가 설정 GET/health/models/workspace/manifest/client bundle/로그에 없음. 입력 전송 POST/PUT body 외 브라우저 영속 저장 없음. 두 프로세스 테스트는 fake transport로 구성하며 실제 fal 요청 0회.
